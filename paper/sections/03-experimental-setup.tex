\section{Experimental Setup}

\label{sec:setup}

\subsection{Consensus Lab Architecture}

The experiments are conducted with the Consensus Lab, a reproducible
benchmark infrastructure that runs the evaluated implementations in a
common containerised environment. Each run is an independent Docker Compose
project containing one coordination service (the upstream EPaxos
master~\cite{moraru2013epaxos} or a lab-provided Raft master), one container
per replica, and one benchmark client. All containers share the same runtime
image and the configured CPU and memory allocations.

Both protocols expose the same benchmark-facing request interface based on
the upstream EPaxos \texttt{genericsmr} wire protocol
(\texttt{PROPOSE} $\rightarrow$ \texttt{ProposeReplyTS}). A single client
binary and workload generator are used for both protocols, so the operation
mix, key-selection process, concurrency control, and request-generation
logic are shared. Request routing differs by protocol architecture: Raft
requests are directed to the current leader reported by the raft master,
whereas EPaxos requests are distributed round-robin across replicas. Reads
are submitted through the consensus path in both protocols; no Raft-specific
local-read optimisation is enabled.

\subsection{Implementation}

Each protocol is represented by two independent implementations. The lab
adapters add only orchestration, monitoring, and the communication-delay
injection described below; they never implement or modify consensus logic.

Raft is provided by \texttt{github.com/hashicorp/raft} v1.7.3
\cite{hashicorpraft}, wrapped in a thin adapter
(\texttt{lab/adapters/raft/}) that converts benchmark requests into
state-machine commands, invokes \texttt{raft.Raft.Apply}, and returns the
response. Leader election, log replication, quorum, commitment, and term
management are performed by the library. Replicas use BoltDB-backed
persistent state in per-replica Docker volumes, with a snapshot threshold of
8{,}192 entries and 1{,}024 trailing logs.

The second Raft implementation uses \texttt{go.etcd.io/raft} v3.7.0
\cite{etcdraft}, wrapped in a lab adapter that follows the library's
asynchronous-storage-writes interface: a dedicated append thread batches log
entries into a single write-ahead-log write with one fsync, mirroring
HashiCorp Raft's group commit. The adapter sets the message-size and
in-flight limits the library requires, enables pre-vote to match HashiCorp
Raft, and compacts its log below the applied index; the exact values are
documented with the adapter in the repository.

EPaxos uses the upstream \texttt{efficient/epaxos} server and master
\cite{moraru2013epaxos}, pinned at commit \texttt{791b115} and executed with
\texttt{-e -exec -dreply}. Replica state is in-memory. The upstream
implementation fixes the dependency-set size at five; the lab extends this
field to support up to nine replicas through a documented wire-format
extension that does not alter the protocol phases, quorums, or decision
rules. The second EPaxos implementation uses
\texttt{nvanbenschoten/epaxos}~\cite{nvbepaxos}, pinned at commit
\texttt{425bd36}, wrapped in a lab adapter
(\texttt{lab/adapters/nvbepaxos/}) that bridges the library's gRPC peer
transport to the benchmark's client protocol. EPaxos state is in-memory in
both implementations.

\subsubsection{Communication-delay injection}

The communication-cost family adds a fixed one-way delay to every
inter-replica message, implemented in each implementation's send path:
HashiCorp Raft's transport wrapper sleeps before forwarding
\texttt{AppendEntries} and \texttt{RequestVote}; the etcd and nvb adapters'
per-peer sender goroutines sleep before writing; and the original EPaxos
\texttt{genericsmr} send path sleeps before each outbound message (the one
place the lab modifies that binary beyond orchestration). The delay is
applied per message, so an implementation that sends more messages per
request, or serialises its sends, is affected more strongly; the etcd
adapter's per-peer sender sleeps on its critical path. The
communication-cost results should therefore be read as measurements of each
implementation's send-path structure under added delay, not as a
protocol-level latency-sensitivity ranking.

Because the implementations use their native storage and execution
mechanisms, the measurements evaluate complete implementations rather than
isolated consensus kernels.

\subsection{Client Harness and Workload Model}

The benchmark client generates requests over a keyspace of 1{,}000 keys with
a configurable read/write composition. The client is closed-loop: one worker
per unit of configured concurrency issues its next request only after the
previous one completes, so the configured concurrency is the maximum number
of in-flight requests. For conflict experiments, a configured conflict ratio
determines the probability that a request selects from a shared hot-key set;
the realised hot-key fraction is measured from the generated sequence rather
than assumed. Workload seeds are recorded for every repetition. Each run
begins with a warm-up phase followed by a measured phase; warm-up requests
are not included in performance measurements.

\subsection{Metrics}

For each request, the client records the run identifier, protocol, replica
count, workload parameters, concurrency, operation, key, target replica,
start and completion timestamps, latency, and success or failure status.
The analysis pipeline derives throughput, success rate, and p50/p95/p99
latency. Per-replica resource telemetry is collected at approximately
200\,ms resolution: CPU from cgroup v2 \texttt{cpu.stat}, network RX/TX
from \texttt{/proc/<pid>/net/dev}, and resident memory from
\texttt{/proc/<pid>/status}. Raw samples are retained per replica.

Each repetition uses a fresh Docker Compose project with new containers,
networks, and volumes. The harness verifies before execution that no
leftover containers, networks, volumes, or ports remain, and verifies
teardown afterwards; a run that fails those checks is recorded as an invalid
attempt rather than silently reused. Configurations are scheduled by blocked
randomisation: each repetition block contains every configuration exactly
once in a seeded shuffled order, and each repetition uses an independent
recorded workload seed.

\subsection{Experiment Suite}

Table~\ref{tab:suite} lists the experiment families. The first seven form
the recorded suite and the last three were added afterwards, each analysed
from its own results subtree and never pooled with the recorded dataset
(Sections~\ref{sec:persistence-results}--\ref{sec:conflict-results}). The
Workload and Concurrency families overlap in concurrency by design: the
Workload family measures the interaction between write ratio and
concurrency, while the Concurrency family isolates the concurrency dimension
at 100\,\% writes and extends it to 256, where the throughput difference is
largest. That overlap also provides a check on run-to-run variability. The
Election family uses the \emph{measured} failed-election count from the
adapters' pre-vote and vote counters rather than the configured target.

Failure injection is deterministic: the runner kills the selected container
with \texttt{docker kill} at a configured offset into the measured phase.
For Raft leader failure, the current leader is obtained from the raft master
and mapped to its container; the client reconnects to the new leader. For
EPaxos replica failure, replica 0 is killed and the client moves to the
remaining replicas. Recovery intervals are reconstructed from request
timestamps and the approximately 200\,ms monitoring resolution and are
therefore approximate.

\subsection{Correctness Validation}

The performance experiments are not a formal verification of consensus
correctness. A separate harness (\texttt{runner correctness}) issues
2{,}000 deterministic requests, each writing a unique key, and compares
replica state snapshots returned by a read-only \texttt{GetState} RPC, so it
does not assume that the two protocols expose equivalent log
representations. Each implementation is tested at concurrency 1, 8, and 32
and under the failure scenarios of the failure family, including a restarted
Raft replica recovering its committed state from its persistent log. This
checks state convergence for the tested scenarios; it is not a general
linearisability proof.

\subsection{Experimental Integrity and Statistical Analysis}

Host-level telemetry (load average, available memory) is recorded at
approximately 200\,ms resolution for every run, and host suspension,
scheduling gaps, CPU starvation, and clock anomalies are detected and
recorded. A run flagged as contaminated is excluded from aggregates and
replaced, so each configuration keeps its planned number of observations;
the replacement is a new attempt and the original remains in the raw
dataset.

All aggregates are computed from raw per-run observations. Because a small
number of repetitions stalled (Section~\ref{sec:evaluation}), throughput
and latency are summarised by the median of the per-repetition values, with
95\,\% confidence intervals from a non-parametric bootstrap (10{,}000
resamples). Protocol differences use the exact Mann-Whitney $U$ test and
workload-trend hypotheses the Kruskal-Wallis test, both without a
multiplicity correction: a quoted $p$-value is the uncorrected value for
that single comparison. The election experiment is treated as a
Raft-specific recovery characterisation reported descriptively, with no
causal interpretation assigned to the measured association.
