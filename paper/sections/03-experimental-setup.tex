\section{Experimental Setup}

\label{sec:setup}

\subsection{Consensus Lab Architecture}

The experiments are conducted with the Consensus Lab, a reproducible
benchmark infrastructure that runs the evaluated implementations in a
common containerised environment. Each run is an independent Docker Compose
project containing one coordination service (the upstream EPaxos
master~\cite{moraru2013epaxos} or a lab-provided Raft master), one container
per replica, and one benchmark client. All containers share the same runtime
image and the configured CPU and memory allocations.

Both protocols expose the same benchmark-facing request interface based on
the upstream EPaxos \texttt{genericsmr} wire protocol
(\texttt{PROPOSE} $\rightarrow$ \texttt{ProposeReplyTS}). A single client
binary and workload generator are used for both protocols, so the operation
mix, key-selection process, concurrency control, and request-generation
logic are shared. Request routing differs by protocol architecture: Raft
requests are directed to the current leader reported by the raft master,
whereas EPaxos requests are distributed round-robin across replicas. Reads
are submitted through the consensus path in both protocols; no Raft-specific
local-read optimisation is enabled.

\subsection{Implementation}

Each protocol is represented by two independent implementations
(Table~\ref{tab:implementations}). The lab adapters add only orchestration,
monitoring, and the communication-delay injection described below; they
never implement or modify consensus logic.

Raft is provided by \texttt{github.com/hashicorp/raft} v1.7.3
\cite{hashicorpraft}, wrapped in a thin adapter
(\texttt{lab/adapters/raft/}) that converts benchmark requests into
state-machine commands, invokes \texttt{raft.Raft.Apply}, and returns the
response. Leader election, log replication, quorum, commitment, and term
management are performed by the library. Replicas use BoltDB-backed
persistent state in per-replica Docker volumes, with a snapshot threshold of
8{,}192 entries and 1{,}024 trailing logs.

The second Raft implementation uses \texttt{go.etcd.io/raft} v3.7.0
\cite{etcdraft}, wrapped in a lab adapter
(\texttt{lab/adapters/etcdraft/}) that follows the library's
asynchronous-storage-writes interface: a dedicated append thread batches up
to 64 log entries into one write-ahead-log write with a single fsync,
mirroring HashiCorp Raft's group commit. The adapter sets
\texttt{MaxSizePerMsg}=4{,}096 and \texttt{MaxInflightMsgs}=256 (the library
provides no defaults), enables pre-vote to match HashiCorp Raft, and
compacts the log below \texttt{applied}~$-$~1{,}024 trailing entries.

EPaxos uses the upstream \texttt{efficient/epaxos} server and master
\cite{moraru2013epaxos}, pinned at commit \texttt{791b115} and executed with
\texttt{-e -exec -dreply}. Replica state is in-memory. The upstream
implementation fixes the dependency-set size at five; the lab extends this
field to support up to nine replicas through a documented wire-format
extension that does not alter the protocol phases, quorums, or decision
rules. The second EPaxos implementation uses
\texttt{nvanbenschoten/epaxos}~\cite{nvbepaxos}, pinned at commit
\texttt{425bd36}, wrapped in a lab adapter
(\texttt{lab/adapters/nvbepaxos/}) that bridges the library's gRPC peer
transport to the benchmark's client protocol.

\subsubsection{Communication-delay injection}

The communication-cost family adds a fixed one-way delay to every
inter-replica message, implemented in each implementation's send path:
HashiCorp Raft's transport wrapper sleeps before forwarding
\texttt{AppendEntries} and \texttt{RequestVote}; the etcd and nvb adapters'
per-peer sender goroutines sleep before writing; and the original EPaxos
\texttt{genericsmr} send path sleeps before each outbound message (the one
place the lab modifies that binary beyond orchestration). The delay is
applied per message, so an implementation that sends more messages per
request, or serialises its sends, is affected more strongly; the etcd
adapter's per-peer sender sleeps on its critical path. The
communication-cost results should therefore be read as measurements of each
implementation's send-path structure under added delay, not as a
protocol-level latency-sensitivity ranking.

Because the implementations use their native storage and execution
mechanisms, the measurements evaluate complete implementations rather than
isolated consensus kernels.

\subsection{Client Harness and Workload Model}

The benchmark client generates requests over a keyspace of 1{,}000 keys with
a configurable read/write composition. The client is closed-loop: one worker
per unit of configured concurrency issues its next request only after the
previous one completes, so the configured concurrency is the maximum number
of in-flight requests. For conflict experiments, a configured conflict ratio
determines the probability that a request selects from a shared hot-key set;
the realised hot-key fraction is measured from the generated sequence rather
than assumed. Workload seeds are recorded for every repetition. Each run
begins with a warm-up phase followed by a measured phase; warm-up requests
are not included in performance measurements.

\subsection{Metrics}

For each request, the client records the run identifier, protocol, replica
count, workload parameters, concurrency, operation, key, target replica,
start and completion timestamps, latency, and success or failure status.
The analysis pipeline derives throughput, success rate, and p50/p95/p99
latency. Per-replica resource telemetry is collected at approximately
200\,ms resolution: CPU from cgroup v2 \texttt{cpu.stat}, network RX/TX
from \texttt{/proc/<pid>/net/dev}, and resident memory from
\texttt{/proc/<pid>/status}. Raw samples are retained per replica.

\subsection{Testbed Configuration and Parameters}

Each performance run consists of a 3-second warm-up followed by a 20-second
measured phase, repeated independently ten times. Each replica container is
allocated 2.0 CPUs and 512\,MB; the client 2.0 CPUs and 512\,MB; the
coordination service 1.0 CPU and 256\,MB. \texttt{GOMAXPROCS} is 4 for all
replicas. The request timeout is 2{,}000\,ms. Raft uses a 1{,}000\,ms
heartbeat timeout, a 2{,}000\,ms election timeout, a snapshot threshold of
8{,}192 entries, and 1{,}024 trailing logs. Raft retains its persistent
state during a run while EPaxos uses in-memory state; this difference is
part of the implementation configuration being measured. Docker volumes are
isolated between repetitions so no consensus state carries over.

To examine sensitivity to communication delay, each outbound inter-replica
message can be delayed by $d = c + U(0, cj/100)$, where $c$ is a fixed
one-way cost in milliseconds (0, 1, 3, 5, 10) and $j$ is a jitter percentage
(0, 5, 10, 50, 100, evaluated at the 5\,ms cost level). This models
application-level message delay rather than a physical network; it does not
reproduce queueing, packet loss, or link-level scheduling.

Each repetition uses a fresh Docker Compose project with new containers,
networks, and volumes. Before execution the harness verifies the environment
is free of leftover containers, networks, volumes, and ports; after
execution it verifies teardown. A run that fails isolation checks is
recorded as an invalid attempt rather than silently reused. Configurations
are scheduled using blocked randomisation: each repetition block contains
every configuration exactly once in a seeded shuffled order, and each
repetition uses an independent workload seed. Both seeds are recorded.

The principal experiment dimensions are replica count (3, 5, 7, 9), write
ratio (0, 10, 50, 90, 100\,\%), conflict ratio (0, 10, 25, 50, 75, 90,
100\,\%), client concurrency (1--256), and communication cost (0, 1, 3, 5,
10\,ms).

\subsection{Experiment Suite}

The experiment suite contains seven families, each evaluated with ten
independent repetitions:

\begin{itemize}

\item \textbf{Workload}: write-ratio (0--100\,\%) and concurrency (1--128)
sweeps at three replicas.

\item \textbf{Scaling}: replica-count sweep (3--9) at 100\,\% writes and
concurrency 32.

\item \textbf{Conflict}: conflict-ratio sweep (0--100\,\%) at three
replicas, 100\,\% writes, concurrency 32.

\item \textbf{Concurrency}: concurrency sweep (1--256) at three replicas,
100\,\% writes. The Workload and Concurrency families overlap in
concurrency (1--128) by design: the Workload family measures the
interaction between write ratio and concurrency, while the Concurrency
family isolates the concurrency dimension at 100\,\% writes and extends it
to 256, where the throughput difference is largest. The overlap also
provides a check on run-to-run variability.

\item \textbf{Communication cost}: one-way delay sweep (0--10\,ms) at three
replicas, 100\,\% writes, concurrency 32, plus a jitter sweep (0--100\,\%)
at the 5\,ms level.

\item \textbf{Election}: Raft leader-election disruption. The leader is
terminated and transport to the survivors is isolated for a nominal target
of 0--5 failed election attempts; the analysis uses the \emph{measured}
failed-election count from the adapters' pre-vote/vote counters, not the
target.

\item \textbf{Failure}: Raft leader kill, Raft follower kill, and EPaxos
replica kill at three replicas, 100\,\% writes, concurrency 32.

\end{itemize}

Failure injection is deterministic: the runner kills the selected container
with \texttt{docker kill} at a configured offset into the measured phase.
For Raft leader failure, the current leader is obtained from the raft master
and mapped to its container; the client reconnects to the new leader. For
EPaxos replica failure, replica 0 is killed and the client moves to the
remaining replicas. Recovery intervals are reconstructed from request
timestamps and the approximately 200\,ms monitoring resolution and are
therefore approximate.

\subsection{Correctness Validation}

The performance experiments are not intended as a formal verification of
consensus correctness. A separate correctness harness
(\texttt{runner correctness}) checks state convergence under the tested
execution and failure scenarios. It issues 2{,}000 deterministic requests,
each writing a unique key derived from its request identifier with a
deterministic value. Each replica exposes a read-only \texttt{GetState} RPC
returning a state snapshot and the applied-command count; the harness
compares replica states rather than internal logs, so it does not assume
that Raft and EPaxos expose equivalent log representations. Each
implementation is tested at concurrency 1, 8, and 32 and under the failure
scenarios of the failure family. Because Raft persists its log, a restarted
Raft replica must recover its committed state; EPaxos uses in-memory state,
so a restarted EPaxos replica is evaluated for liveness and subsequent
participation. This validation checks state convergence for the tested
scenarios; it does not constitute a general linearizability proof.

\subsection{Experimental Integrity and Statistical Analysis}

Host-level telemetry (load average, available memory) is recorded at
approximately 200\,ms resolution for every run. Host suspension, scheduling
gaps, CPU starvation, and clock anomalies are detected and recorded. A run
flagged as contaminated is excluded from aggregates and replaced so each
configuration retains its planned number of observations; the replacement
is recorded as a separate attempt and the original remains in the raw
dataset.

All aggregates are computed from raw per-run observations. Because a small
number of repetitions stalled (Section~\ref{sec:evaluation}), throughput
and latency are summarised by the median of the per-repetition values, with
95\,\% confidence intervals from non-parametric bootstrap (10{,}000
resamples). Protocol differences are tested with the exact Mann-Whitney
$U$ test and workload-trend hypotheses with the Kruskal-Wallis test; no
multiplicity correction is applied. Latency is reported as p50/p95/p99.
The election experiment is treated as a Raft-specific recovery
characterisation reported descriptively, with no causal interpretation
assigned to the measured association.
