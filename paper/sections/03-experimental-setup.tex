\section{Experimental Setup}
\label{sec:setup}

\subsection{Consensus Lab Architecture}

The experiments are conducted with the Consensus Lab, a reproducible benchmark
infrastructure that runs both protocols in the same execution environment.
Each run is a Docker Compose project with one container per role: a
coordination service (the upstream EPaxos master \cite{moraru2013epaxos}, or
the lab's raft master which mirrors its RPC surface), one container per
replica, and a benchmark client. All containers share a single runtime image
and identical CPU and memory allocations.

Both protocols expose the same benchmark-facing interface: the upstream
EPaxos \texttt{genericsmr} wire protocol (\texttt{PROPOSE} $\rightarrow$
\texttt{ProposeReplyTS}). A single client binary drives both protocols with
the same workload generator, so the op mix, key distribution, and timing are
identical. The only protocol-intrinsic difference is endpoint selection:
Raft sends every request to the leader reported by HashiCorp Raft, while
EPaxos spreads requests round-robin across replicas. Reads are routed through
consensus in both protocols; there is no Raft-only local-read optimisation.

\subsection{Implementation}

Raft is provided by \texttt{github.com/hashicorp/raft} v1.7.3
\cite{hashicorpraft}, wrapped in a thin adapter
(\texttt{lab/adapters/raft/}) that converts benchmark requests into
state-machine commands, calls \texttt{raft.Raft.Apply}, waits for the
resulting future, and returns the response. HashiCorp Raft performs leader
election, log replication, quorum calculation, commit logic, term management,
and state transitions; the adapter never elects or selects a leader. Raft
replicas persist state to named volumes (boltdb).

EPaxos uses the upstream \texttt{efficient/epaxos} server and master
unchanged \cite{moraru2013epaxos} (pinned commit \texttt{791b115}, run with
\texttt{-e -exec -dreply}). The lab only adds external orchestration:
containers, monitoring, and failure injection. EPaxos replicas keep state in
memory (upstream default). The vendored upstream hardcodes the
dependency-set size to 5; the lab extends it to 9 via a documented
wire-format extension so that 7- and 9-replica clusters run. The protocol's
phases, quorums, and decision rules are unchanged, and all replicas run the
same patched binary.

\subsection{Client Harness and Workload Model}

The client generates requests with a configurable read/write mix over a
keyspace of 1{,}000 keys. Write ratio is expressed as the percentage of
requests that are writes; the remainder are reads. The client is closed-loop:
it runs one worker per unit of configured concurrency, and each worker issues
its next request only after the previous request completes, so the configured
concurrency is the maximum number of in-flight requests. Both protocols
receive the same workload. With probability equal to the configured conflict
rate, a request targets one of the shared hot keys; otherwise it targets a
uniformly random key from the disjoint cold range, so the realised hot-key
fraction is exact. A warm-up phase precedes the measured phase, and warm-up
requests are not recorded.

\subsection{Metrics}

For every request, the client records the run ID, protocol, replica count,
workload ratio, concurrency, operation, key, target replica, start and end
timestamps, latency, and success or failure. From these records the
processing pipeline computes throughput (requests per second), success rate,
and p50/p95/p99 latency distributions.

Per-replica resource samples are collected from the host at approximately
200\,ms resolution: CPU from cgroup v2 \texttt{cpu.stat}, network RX/TX from
\texttt{/proc/\allowbreak{}<pid>/\allowbreak{}net/\allowbreak{}dev} in the
container's network namespace, and memory (RSS) from
\texttt{/proc/\allowbreak{}<pid>/\allowbreak{}status}. Raw samples are stored
per replica without aggregation, so that workload distribution across
replicas can be examined.

\subsection{Testbed Configuration and Parameters}

All runs use a 20-second measured phase with a 3-second warm-up and ten
independent repetitions. Each replica container is allocated 2.0 CPUs and
512\,MB of memory; the client gets 2.0 CPUs and 512\,MB, and the master
1.0 CPU and 256\,MB. \texttt{GOMAXPROCS} is set to 4 for every replica in
both protocols. The request timeout is 2{,}000\,ms. Raft uses a 1{,}000\,ms
heartbeat timeout, a 2{,}000\,ms election timeout, a snapshot threshold of
8{,}192 entries, and 1{,}024 trailing logs.

To evaluate the protocols under more realistic network conditions, the
benchmark can inject a fixed one-way latency into every inter-replica
message, optionally with jitter. The injection is implemented in the
adapters' send path: each outbound message waits a configurable cost plus a
uniform random delay before being written to the socket. The cost $c$ is
expressed in milliseconds (0, 1, 3, 5, 10); jitter $j$ is a percentage of
the cost (0, 5, 10, 50, 100\,\%), so a message at cost $c$ and jitter $j$
waits $c + U(0, c \cdot j/100)$ milliseconds. The baseline (cost 0) is the
local-network configuration used by every other experiment family; the
jitter sweep is evaluated only at the 5\,ms cost level to keep the matrix
bounded.

Each repetition is a fresh Docker Compose project: new containers, new
networks, and new volumes. Raft's persisted state (term, voted-for, log,
snapshots, cluster membership) lives in per-replica volumes that are
destroyed after every repetition and verified removed; persistence is not
part of any experiment, so no consensus state survives between repetitions.
EPaxos state is in-memory by construction. Before each repetition the
harness verifies that the environment is clean (ports free, no leftover
containers, volumes, or networks); after each repetition it verifies that
teardown removed everything. A repetition that cannot be isolated is
recorded as failed, never silently reused.

To prevent experimental conditions from being confounded with wall-clock
time, conditions are not executed in blocks. Instead, the runner uses
blocked randomization: repetition block $b$ contains every configuration
exactly once, in an order shuffled with a seeded random number generator.
The schedule seed is recorded, so the exact execution order is
reproducible. Each repetition uses an independent workload seed (base seed
plus repetition index), recorded in the run's metadata, so no two
repetitions replay the same workload sequence and any anomalous run can be
reproduced exactly.

The experiment dimensions are: replica count (3, 5, 7, 9), write ratio
(0, 10, 50, 90, 100\,\%), conflict ratio (0, 10, 25, 50, 75, 90, 100\,\%),
client concurrency (1, 2, 4, 8, 16, 32, 64, 128, 256), and one-way
communication cost (0, 1, 3, 5, 10\,ms) with jitter (0, 5, 10, 50,
100\,\%).

\subsection{Experiment Suite}

The experiment suite consists of seven families, each with ten repetitions:

\begin{itemize}
\item \textbf{Workload}: write-ratio (0, 10, 50, 90, 100\,\%) $\times$
  concurrency (1--128) sweep at 3 replicas, 2 protocols.
\item \textbf{Scaling}: replica count sweep (3--9) at 100\,\% writes and
  concurrency 32, 2 protocols.
\item \textbf{Conflict}: conflict ratio sweep (0--100\,\%) at 3 replicas,
  100\,\% writes, and concurrency 32, 2 protocols.
\item \textbf{Concurrency}: concurrency sweep (1--256) at 3 replicas and
  100\,\% writes, 2 protocols.
\item \textbf{Communication cost}: one-way latency sweep (0, 1, 3, 5,
  10\,ms) at 3 replicas, 100\,\% writes, and concurrency 32, followed by a
  jitter sweep (0, 5, 10, 50, 100\,\%) at the 5\,ms cost level, 2 protocols.
\item \textbf{Election}: Raft leader-election disruption: the leader is
  killed and the surviving replicas' Raft transport is isolated for a target
  number of failed election attempts (0--5). The independent variable is the
  \emph{measured} number of failed elections (derived from the Raft
  adapters' dropped pre-vote and vote counters), not the configured target;
  the target is a nominal setting only. The measured phase is long enough
  for the longest isolation to expire and recovery to complete; a run whose
  cluster does not recover within the phase is recorded as failed.
\item \textbf{Failure}: Raft leader kill, Raft follower kill, and EPaxos
  replica kill at 3 replicas, 100\,\% writes, and concurrency 32.
\end{itemize}

Failure injection is deterministic: the runner kills a container with
\texttt{docker kill} at a configured offset into the measured phase. For Raft
leader failure, the runner queries the raft master for the current leader,
maps it to the container hostname, and kills it; the client observes the
election and reconnects to the new leader. For EPaxos replica failure,
replica 0 is killed and the client moves to the next replica. Recovery
timing is reconstructed from request timestamps and the approximately
200\,ms monitor resolution, and is therefore approximate.

Host-level telemetry (load average and available memory, sampled at
200\,ms) is recorded for every run. Host suspension, scheduling gaps, CPU
starvation, and clock jumps are detected and recorded per run. Anomalous
runs are marked and reported; they are never silently deleted.

The exclusion rule is fixed in advance and applied uniformly to every
condition: a run whose host telemetry was flagged contaminated is excluded
from every aggregate, and the lost observation is replaced by re-running
that repetition, so each condition keeps its full set of independent
repetitions. A replacement is a separate run recording which attempt it
replaces and why; the original attempt stays in the dataset. Excluded and
replacement runs are reported, and the Execution Integrity section of the
accompanying report states how many runs were affected.

All aggregates are computed from the raw per-run observations. Each
configuration is evaluated over ten independent repetitions; means are
reported with sample standard deviation and 95\,\% confidence intervals
(Student's $t$). Latency
distributions are reported as p50/p95/p99. For the election experiment we
report the Pearson correlation between the measured number of failed
elections and the availability gap, with $n$ and a $t$-based $p$-value, and
we plot every observation. Outliers within clean runs are not removed.
