\section{Threats to Validity}

\label{sec:threats}

\subsection{External Validity}

All replicas run on a single host over a bridge network, so the measurements
contain no wide-area latency, no real packet loss, and no multi-machine
failure domains. The host is a WSL2 environment with 12 physical cores,
placing a virtualisation layer between the containers and the hardware.
Cluster sizes are 3--9, the keyspace is 1{,}000 keys, commands are uniform
in size, and the measured phase is 20\,s. The results therefore describe
short, uniform, single-host runs rather than long-lived deployments with
skewed access patterns, large payloads, or geographically distributed
replicas.

The configured CPU quotas exceed the physical core count at the larger
cluster sizes (nine replicas at 2.0 CPUs each plus client and master
request 21 CPUs against 12 cores), but the measured host load average stayed
at 3.8--5.1 across the scaling family and the per-replica CPU means imply
roughly 4--5 cores of actual demand, so the host was not CPU-saturated and
the throughput decline with replica count is not explained by host
saturation. Each replica is allocated 2.0 CPUs while \texttt{GOMAXPROCS}=4,
so the Go scheduler parallelism exceeds the container quota; the resulting
interaction with cgroup throttling is part of the measured environment.

Reads are routed through consensus in both protocols and no Raft-specific
read optimisation is enabled, so the read comparison is of equivalent
consensus-facing paths rather than each system's fastest possible read
path. Both systems are measured with identical CPU and memory allocations,
which provides a controlled comparison but not a resource-tuned deployment.

Persistence is a source of asymmetry between the protocols: both Raft
implementations persist their log (BoltDB, or a write-ahead log with batched
fsync) while both EPaxos implementations keep state in memory, and the Raft
adapters compact their logs (snapshot threshold 8{,}192 entries, 1{,}024
trailing logs), so snapshot and compaction work is part of the steady-state
Raft path. The latency and throughput differences therefore include the cost
of persistence and log maintenance, which is a property of the evaluated
implementations, not of the protocols themselves. The EPaxos implementation
is additionally modified to support the dependency-set sizes required by the
7- and 9-replica configurations; results at those sizes should not be
interpreted as isolating the cost of the EPaxos protocol from the cost of
this extension.

The communication experiment injects delay in the application-level
outbound message path rather than through a physical network emulator, so it
does not reproduce queueing, packet loss, or link-level scheduling, and the
jitter experiment changes the mean delay when jitter is increased. The
failure and election experiments use three replicas, so their recovery times
characterise that configuration only; the failure scenarios are also not
symmetric (the Raft leader-failure experiment removes the normal request
endpoint, whereas the follower- and replica-failure experiments remove a
non-central replica). The Raft leader-recovery interval depends on the
configured heartbeat and election-timeout parameters and on client timeout
and reconnection behaviour.

The correctness harness verifies state convergence under the tested
workloads and restart scenarios but does not constitute a formal
verification of consensus correctness or establish general linearizability;
the unique-key workload does not exercise conflicting operations on the same
state in a way that would expose every possible ordering violation.

\subsection{Statistical Conclusion Validity}

Each configuration is measured ten times, and aggregates are reported as
medians with non-parametric bootstrap 95\,\% confidence intervals. Ten
repetitions leave substantial uncertainty: measuring the same nominal
configuration in four steady-state families produced medians that differed
by 2--3\,\% for both protocols, and the bootstrap intervals overlap in
several comparisons whose medians differ, such as at seven and nine
replicas. We therefore treat overlapping comparisons as inconclusive rather
than as evidence of a small but established effect.

The suite contains many configurations and pairwise comparisons without a
global multiplicity correction, so an isolated statistically detectable
difference should not be interpreted as strong evidence for a general
effect. The election correlation analysis requires particular caution: the
measured failed-election count is an outcome of the recovery process and is
mechanically related to the injected isolation duration, and the 60 runs are
grouped by six isolation targets (ten runs each), so the observations are
not fully independent and the reported $p$-values are optimistic. The
correlation should be read as a descriptive association, not as a
hypothesis test with 60 independent observations.

The 20\,s measurement window limits the characterisation of long-term
steady-state behaviour, and the closed-loop client means the configured
concurrency is a maximum number of in-flight requests rather than an
independently controlled arrival rate. Outliers within clean runs are not
removed; runs identified as affected by environmental interference are
investigated separately and are not excluded solely because their
performance is inconvenient for the comparison.
