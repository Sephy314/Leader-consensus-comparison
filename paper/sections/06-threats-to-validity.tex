\section{Threats to Validity}

\label{sec:threats}

\subsection{External Validity}

All replicas run on a single host over a bridge network, so the measurements
contain no wide-area latency, no real packet loss, and no multi-machine
failure domains. The host is a WSL2 environment with 12 physical cores,
placing a virtualisation layer between the containers and the hardware.
Cluster sizes are 3--9, the keyspace is 1{,}000 keys, commands are uniform
in size, and the measured phase is 20\,s. The results therefore describe
short, uniform, single-host runs rather than long-lived deployments with
skewed access patterns, large payloads, or geographically distributed
replicas.

The larger cluster sizes also introduce physical resource contention that
cannot be completely separated from the replica-count effect. Nine
replicas at 2.0 CPU requests each, together with the client and master,
request 21 CPUs against a 12-core host. In addition, each replica is
allocated 2.0 CPUs while \texttt{GOMAXPROCS}=4, so Go scheduler parallelism
exceeds the container CPU quota. Consequently, the 7- and 9-replica
configurations should be interpreted as measurements under a
resource-constrained local environment rather than as isolated evidence of
protocol-level scaling. These configurations are retained because they
represent the behaviour of the evaluated systems in this environment, but
the 3- and 5-replica configurations provide a less resource-contended basis
for the primary scaling comparison.

Reads are routed through consensus in both protocols and no Raft-specific
read optimisation is enabled, so the read comparison is of equivalent
consensus-facing paths rather than each system's fastest possible read path.
Both systems are measured with identical CPU and memory allocations, which
provides a controlled comparison but not a resource-tuned deployment.

Persistence is a source of implementation asymmetry. In the original
baseline, the evaluated Raft implementations use persistent storage, while
the EPaxos implementations use in-memory state. In particular, the nvb
EPaxos implementation does not provide a built-in durable storage backend;
no new persistence mechanism is implemented for this study. Consequently,
the original latency and throughput measurements may include persistence
costs that are specific to the evaluated implementations rather than to the
consensus protocols themselves. A separate persistence-control experiment
therefore evaluates memory and durable configurations where the respective
implementations support both modes; its results are reported in
Section~\ref{sec:persistence-results} and show that the recorded ordering
depends on which storage mode each implementation was run in. The nvb
implementation is evaluated only in its supported in-memory configuration.

The EPaxos implementation is additionally modified to support the
dependency-set sizes required by the 7- and 9-replica configurations.
Results at those sizes therefore combine the protocol behaviour with the
cost of the required implementation extension. This further motivates
interpreting the larger-cluster results as resource- and
implementation-sensitive measurements rather than as isolated estimates of
protocol scaling.

The controlled network-delay experiment applies fixed one-way delay to
inter-replica traffic using operating-system-level network emulation rather
than application-level sleeps. The delay is scoped to peer-to-peer replica
traffic, leaving client-to-replica traffic unaffected. This approach avoids
the adapter-level serialisation effects of application-level delay
injection, but it still does not reproduce the full behaviour of a
distributed physical network, including packet loss, congestion,
multi-hop routing, or independent link failures. The earlier
application-level delay and jitter measurements are retained as legacy
experiments but are not treated as the primary evidence for clean network
delay sensitivity (Section~\ref{sec:delay-results}); jitter is not included
in the controlled delay experiment.

The conflict ratio is specified through the workload's key-access pattern,
but the configured percentage does not by itself establish the amount of
protocol-level contention observed by EPaxos. The conflict-validation
experiment therefore records the realised hot-key access pattern together
with available protocol-level execution indicators, including fast- and
slow-path behaviour where exposed by the implementation
(Section~\ref{sec:conflict-results}). Conclusions about
conflict sensitivity are limited to effects supported by both the workload
configuration and these observed execution characteristics.

The failure and election experiments use three replicas, so their recovery
times characterise that configuration only. The failure scenarios are also
not symmetric: the Raft leader-failure experiment removes the normal
request endpoint, whereas the follower- and replica-failure experiments
remove a non-central replica. The Raft leader-recovery interval depends on
the configured heartbeat interval and election timeout, as well as on
client timeout and reconnection behaviour. These parameters are therefore
reported explicitly, and the measured availability gap is interpreted as
a result under the specified failure-detection configuration rather than
as an implementation-independent recovery time for Raft.

The correctness harness verifies state convergence under the tested
workloads and restart scenarios but does not constitute a formal
verification of consensus correctness or establish general linearizability.
In particular, the tested workloads do not exercise every possible pattern
of conflicting operations and message reordering that could expose an
ordering violation.

\subsection{Statistical Conclusion Validity}

Each configuration is measured ten times, and aggregates are reported as
medians with non-parametric bootstrap 95\,\% confidence intervals. Ten
repetitions leave substantial uncertainty: measuring the same nominal
configuration in four steady-state families produced medians that differed
by 2--3\,\% for both protocols, and the bootstrap intervals overlap in
several comparisons whose medians differ, such as at seven and nine
replicas. We therefore treat overlapping comparisons as inconclusive rather
than as evidence of a small but established effect.

The suite contains many configurations and pairwise comparisons, and no
multiplicity correction is applied (Section~\ref{sec:setup}): a $p$-value
quoted in the evaluation is the uncorrected value for that single
comparison. Tests are reported next to the family they belong to, so the
number of comparisons behind a claim is visible, and we rely on comparisons
that are well separated rather than on borderline significance.

The election correlation analysis requires particular caution: the measured
failed-election count is an outcome of the recovery process and is
mechanically related to the injected isolation duration, and the 60 runs
are grouped by six isolation targets (ten runs each). The observations
should therefore not be treated as 60 fully independent samples. The
correlation is interpreted primarily as a descriptive association rather
than as independent evidence of a general causal relationship.

The 20\,s measurement window limits the characterisation of long-term
steady-state behaviour, and the closed-loop client means the configured
concurrency is a maximum number of in-flight requests rather than an
independently controlled arrival rate. Outliers within clean runs are not
removed; runs identified as affected by environmental interference are
investigated separately and are not excluded solely because their
performance is inconvenient for the comparison.
