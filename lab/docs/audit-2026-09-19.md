# Benchmark Reliability Audit — 2026-09-19

This document is the complete audit of the benchmark/test suite in `lab/`,
performed before the reliability redesign. It inventories every test,
documents what is measured and how, and lists the methodological problems
found. It is the basis for the changes described in
`lab/docs/benchmark-protocol-v2.md`.

The audit covers:

1. Every test in the suite (unit tests, smoke tests, measured experiments).
2. Repetition counts, warm-up behaviour, isolation, state persistence,
   randomness, timing, and statistical treatment for each.
3. A numbered list of methodology problems (P1–P12).

### 1.3 Measured experiments (the matrix)

All six families run with `duration_s=20`, `warmup_s=3`, `repetitions=3`,
`seed=42`, 2.0 CPU / 512 MB per replica, `GOMAXPROCS=4`, Raft heartbeat
1000 ms / election 2000 ms. Each run is a fresh Docker Compose project
(unique project name = run ID), torn down with `down -v` (volumes removed),
so Raft boltdb state does not persist between runs.

| Family | Independent variable | Configs | Reps | Runs (3 reps) | Measured |
|---|---|---|---|---|---|
| Workload | read% × concurrency | 5 × 8 × 2 proto = 80 | 3 | 240 | throughput, p50/p95/p99, success rate |
| Scaling | replica count (3,5,7,9) | 4 × 2 = 8 | 3 | 24 | throughput, latency |
| Conflict | conflict% (0–100) | 7 × 2 = 14 | 3 | 42 | throughput, latency, fast/slow path |
| Concurrency | concurrency (1–256) | 9 × 2 = 18 | 3 | 54 | throughput, latency |
| Election | target failed elections (0–5) | 6 × 1 = 6 | 3 | 18 | availability gap, recovery time |
| Failure | leader/follower/replica kill | 3 | 3 | 9 | availability gap, failed requests |

Total: 129 configurations, 387 runs at 3 repetitions. The current
`results/raw/` contains 426 runs (extra runs are re-runs with `-2`/`-3`
suffixes after documented host-level CPU starvation).

#### Per-family measurement detail

**Workload / Scaling / Conflict / Concurrency.** The client runs a warm-up
phase (no recording), then a measured phase; `phase.json` marks the measured
phase start. Every request is recorded (op, key, hot flag, target, start/end
ns, latency, ok, error). Throughput = ok requests / measured-phase duration.
Latency percentiles from per-request latencies. Per-replica CPU/net/RSS
sampled at ~200 ms from the host.

**Election.** The runner kills the current Raft leader, then asks every
surviving replica to isolate its Raft transport (drop `RequestVote`/
`RequestPreVote`) for `FailedElections × election_timeout` ms. The isolation
expires automatically; the next election succeeds. Recovery is measured two
ways: (a) the request-based availability gap (largest interval with no
successful completion at/after the kill), and (b) the event-based recovery
time (failure_injected → first valid `leader_observed`).

**Failure.** The runner kills the target container at `at_s` into the
measured phase (leader via master lookup, follower via `pickFollower`,
EPaxos replica 0). No restart. Availability gap and failed-request counts
are derived from request timestamps.

## 3. Methodology problems

### P1 — Insufficient repetitions (n=3 everywhere)
`configs/matrix.json` sets `repetitions: 3` for every family. The paper
reports ranges and trends (e.g. "gaps increase with the number of failed
elections") from n=3 per point. Three independent observations cannot
support the dispersion and trend claims made. **Fix:** ≥10 independent
repetitions per configuration, enforced by the runner (fail loudly below
the minimum), with the minimum documented.

### P2 — Election run IDs do not encode the independent variable
`runIDFor` switches on `experimentName(cfg)`. The matrix sets
`Experiment="election"`, which hits the `default` case and produces
`election-raft-r3-w100-c32-<rep>` — the `failed_elections` target is **not**
in the ID. The `makeRunDir` dedup suffix (`-2`, `-3`, …) then conflates the
independent variable with the repetition: in the current dataset
`election-raft-r3-w100-c32-1-2` is target 2, `-1-3` is target 3, etc. The
target↔run mapping is recoverable only via `metadata.json`. The unit test
misses this because it exercises the derived `failure` path, not the matrix
`election` path. **Fix:** encode the target in the run ID
(`election-raft-r3-e2-1`) and add a test that exercises the matrix path.

### P3 — The actual number of failed elections is never measured
The paper states "the actual number of failed elections is measured from the
leader-election log transitions rather than assumed", but neither the runner
nor the report computes it. The report's election table and figure use the
*target* from metadata. The `leader_observed` transitions in `events.csv`
cannot reveal failed election attempts (a failed attempt does not change the
reported leader; it stays −1). **Fix:** instrument the Raft adapter to count
election attempts (candidate state transitions while the transport is
isolated) and expose them via RPC; the report must use the measured count.

### P4 — Isolation duration is coupled to the election timeout
`isoMS = FailedElections × RaftElectionMS`. HashiCorp Raft randomizes
election timeouts in `[ElectionTimeout, 2×ElectionTimeout]`, so the number
of failed elections that actually occur in a fixed isolation window is
stochastic and may differ from the target. The target is a nominal setting;
only the measured count (P3) is a valid independent variable.

### P5 — Fixed seed for every repetition
`seed: 42` in defaults; the client seeds each worker with `seed + worker_id`.
Every repetition of a configuration therefore replays the identical workload
sequence. Independent repetitions should use independent seeds (configurable,
recorded, reproducible). **Fix:** derive a per-repetition seed
(`base + rep`), pass it to the client, and record the seed actually used in
`metadata.json`.

### P6 — No pre-flight or post-teardown isolation verification
Fixed host ports (17087, 18070+i) and per-run Compose projects. If a previous
run leaked containers (runner crash, `docker` failure), the next run fails to
bind ports or collides. There is no check before a run that the ports are
free, and no verification after teardown that no containers remain.
**Fix:** pre-flight port check; post-teardown container verification recorded
in metadata.

### P7 — Re-run dedup suffix mixes datasets in the report
`makeRunDir` appends `-2`, `-3`, … when a directory exists, so re-running the
matrix creates new directories alongside old ones. The report aggregates
**all** valid runs for a configuration, mixing runs from different host
conditions (the git history documents host-level CPU starvation and
re-runs). `figures.py` has a fragile re-run-selection heuristic
(`len(run_id.split("-")) >= 7`) for specific configurations. **Fix:** archive
the pre-audit dataset, run the new suite into a clean `results/raw`, and add
a `batch_id` to metadata so the report can be scoped to a dataset.

### P8 — Resource samples include warm-up
`resources.csv` spans the whole run (compose up → client exit), including
warm-up and teardown. The report computes CPU utilisation over the full
span. **Fix:** filter resource samples to the measured phase
(`phase.json` start → last request end) in `process.py`.

### P9 — No statistical treatment in the report
The report shows per-config means and ranges but no standard deviation,
confidence intervals, or per-config n in most tables; the election
experiment has no correlation coefficient, no sample size statement, and no
significance measure. **Fix:** report n, mean, median, SD, 95% CI; for the
election experiment report Pearson r, n, CI, and a significance measure, and
plot the actual observations.

### P10 — Smoke runs pollute the measured dataset
Smoke tests write into `results/raw/` (1-rep runs) which the report then
aggregates. **Fix:** write smoke runs to `results/smoke-raw/`.

### P11 — Two inconsistent recovery metrics for the election experiment
`html.py`'s election table uses the event-based recovery time
(`leader_observed` after `failure_injected`), while the publication figure
uses the request-based availability gap. The two can disagree (the gap
includes client reconnect time; the event time does not). **Fix:** use one
primary metric (the request-based availability gap, which is what the paper
reports) and document the other as a secondary diagnostic.

### P12 — No final-state verification
A run is marked successful if `requests.csv` has ≥1 success and
`resources.csv` is non-empty. For failure/election runs there is no check
that the system actually recovered (e.g. a new leader was elected after the
kill). **Fix:** for failure runs, require a valid `leader_observed` after
`failure_injected` (Raft) / successful requests after the kill (EPaxos).

## 4. What is sound

The following are already correct and must be preserved:

- **Process-level isolation per run**: fresh Compose project, `down -v`
  removes volumes; Raft boltdb state does not persist between runs.
- **Warm-up is separated from measurement** for request metrics
  (`phase.json` marks the measured phase; warm-up requests are not recorded).
- **Failed runs are recorded, not deleted**: `run-index.csv` (append-only)
  and `metadata.json` status; the report excludes them from aggregation but
  lists them.
- **Raw observations are first-class**: per-request CSV with full metadata;
  per-replica resource samples stored raw (cumulative counters).
- **No hardcoded summaries**: the report is generated from the raw data.
- **Deterministic failure injection**: kill at a fixed offset into the
  measured phase, leader resolved via the master at injection time.
- **Both protocols share one client and one workload generator**; the only
  difference is endpoint selection, which is protocol-intrinsic and
  documented.
- **Versions and host environment are recorded** in `metadata.json`.

## 5. Election-experiment follow-up analysis (2026-09-20)

The revised protocol (P1–P12 fixes) was implemented and the full matrix
re-run at 10 repetitions. After the re-run, the election experiment was
re-examined for a subtler methodological issue: the availability-gap metric
itself.

### 5.1 The gap metric includes the isolation duration (mechanical correlation)

The election experiment's independent variable is the *measured* number of
failed elections, and the dependent variable is the request-based
availability gap (largest interval with no successful completion after the
leader kill). The injection works by isolating the surviving replicas'
Raft transport for `isoMS = target × election_timeout` ms. The availability
gap therefore **includes the isolation duration by construction**: a run
with target 5 is isolated for 10 s, so its gap cannot be smaller than
~10 s, while a run with target 0 is isolated for 0 s. A positive
correlation between the gap and the measured election count is therefore
**partly mechanical** — it does not by itself show that the cluster takes
longer to recover after more failed elections; it shows that the injection
lasts longer.

This is not a bug in the runner (the isolation duration is the mechanism
that induces N failed elections), but it means the gap correlation must be
interpreted carefully: it conflates the injection duration with the
recovery behaviour.

### 5.2 Decoupled recovery metric

To separate the two, the processing pipeline now computes a second metric,
`recovery_from_isolation_end_s`: the time from the **end of the isolation
window** (latest `election_isolation_confirmed` timestamp + `isoMS`) to the
first successful request. This is decoupled from the injection duration and
measures only the recovery behaviour after the injection has expired
(election + client reconnect).

Interpretation:

- If `recovery_from_isolation_end` is roughly constant across the measured
  election count, the gap correlation is fully explained by the injection
  mechanism (each failed election consumes one election timeout by
  construction).
- If it grows with the measured election count, the cluster needs extra
  time to stabilise after many failed elections (e.g. log catch-up, client
  reconnect storms).

The report and the publication figure now show **both** metrics with their
correlations, and the interpretation is left to the data.

### 5.3 The measured-election proxy

The measured election count is derived from the Raft adapters' dropped
message counters: `(dropped_pre_votes + dropped_votes) / (replicas − 1)`.
This is a proxy, not a direct count of candidate state transitions:

- Each failed attempt produces at least one dropped pre-vote per peer, but
  the exact number depends on how many peers are reachable (the killed
  leader's peer is not), whether the pre-vote round completed before the
  isolation was applied (producing dropped votes as well), and whether both
  survivors attempt simultaneously.
- The proxy is therefore a monotone but biased estimate of the true number
  of failed attempts; the bias is roughly linear in the isolation duration,
  so the correlation direction is preserved, but the x-axis values are
  approximate.

The proxy is documented in `benchmark-protocol-v2.md` §9 and in the report;
it is deterministic and recorded per run. A direct count of candidate state
transitions would require instrumenting HashiCorp Raft's state machine,
which the adapter deliberately does not modify; the proxy is the least
invasive measurement that is monotone in the treatment.

### 5.4 What the re-run showed

The revised dataset (10 repetitions per target, targets 0–5, measured
counts spanning 0–13) reproduces the positive gap correlation. The
decoupled metric determines whether the correlation is mechanical or
reflects genuine recovery behaviour; the report and the methodology-change
report state the result objectively, whichever way it falls.

## 6. Defects found while running the revised suite (2026-09-20)

### P13 — Configuration aggregates conflate experiment families

`process.py:config_key` (the grouping key for `config-summary.csv` and every
report figure) contained the numeric parameters but **not the experiment
family**. Four families share every numeric parameter at their r3/100%-write/
c32 point:

| family | run ID | protocol | r | R/W | c | conflict |
|---|---|---|---|---|---|---|
| workload | `workload-raft-r3-w100-c32-*` | raft | 3 | 0/100 | 32 | 0 |
| concurrency | `concurrency-raft-r3-w100-c32-*` | raft | 3 | 0/100 | 32 | 0 |
| conflict | `conflict-raft-r3-x0-w100-c32-*` | raft | 3 | 0/100 | 32 | 0 |
| scaling | `scaling-raft-r3-w100-c32-*` | raft | 3 | 0/100 | 32 | 0 |

so each of those four conditions was merged into a single aggregate row (and
the corresponding figure points were plotted from mixed conditions). The
pre-audit `config-summary.csv` shows the symptom: per-group `n` values of 18
and 15 where a single condition can only ever contribute 3 (pre-audit) or 10
(revised).

The defect did not change any *comparison* conclusion — every merged group
contains the same protocols with the same parameters, so a ratio of Raft to
EPaxos is unaffected — but every absolute number attributed to those
conditions was averaged over four different experiments.

Fixed by adding the family to the key (`process.py:config_key`), exposing
`experiment` on every metrics/resource row, and replacing the run-ID prefix
tests in `figures.py` / `paper_numbers.py` with that column. Regression test:
`report/test_pipeline.py::test_experiment_families_are_not_conflated`.

### Run selection: contaminated runs and replacement attempts

The protocol requires contaminated runs to be recorded, never silently
deleted, and excluded from aggregates. That rule now lives in one place
(`process.py:mark_included`) and is applied uniformly:

1. A run whose host telemetry was flagged contaminated is excluded.
2. A replacement run (`runner matrix --rerun-contaminated`) takes precedence
   over the attempt it replaces, so a condition keeps one observation per
   planned repetition. The replacement is written to a new run ID
   (`<id>-2`) recording `rerun_of` and `rerun_reason`; the original is kept.
3. Excluded runs stay in `metrics.csv` (`included=0`), `run-index.json`, and
   the execution manifest; `config-summary.csv` reports `n_observed` next to
   `n`, and the report's Execution Integrity section shows the count.

Without rule 2 the exclusion would silently reduce n below the required 10
per condition. Host suspend (WSL2 host sleeping) is the contamination
actually observed: the wall clock jumps while the process is frozen, so it
appears as a multi-second telemetry gap inside a run's measured phase.

### Interrupted batch: the dataset spans two batches

The suite was killed by the host at run 956/1290 (955 runs complete, one
truncated: `conflict-raft-r3-x0-w100-c32-8`). Handling, all documented in
`benchmark-protocol-v2.md` §12:

- the truncated directory and its compose project were archived to
  `results/archive/interrupted-2026-09-20/` and torn down;
- `runner matrix --skip-existing` resumed the suite with the **same schedule
  seed**; it restarted at schedule index 956/1290, confirming that the
  schedule is a pure function of the configuration list and the seed, and
  that the resumed batch executes exactly the missing runs at their original
  positions;
- the execution manifest is now rebuilt from **all** completed runs in
  `results/raw` (not just the current invocation), lists every batch ID, and
  can be regenerated without running anything (`runner manifest`);
- the manifest therefore reports the ~7 h wall-clock gap between batches,
  rather than hiding it.

### What the exclusion rule changed (worked example)

Two of the 60 election runs were flagged contaminated: both contained a
multi-minute host pause *inside* the measured phase (telemetry gaps of 914 s
and 20.5 s on one run; CPU starvation on the other), so their request
timestamps span a frozen host rather than a running cluster. With those two
runs included, the correlation between the measured number of failed
elections and the availability gap is r = 0.188 (p = 0.14, n = 62) — no
relationship. With the documented rule applied (excluded, and the repetition
replaced) it is r = 0.896 (p < 1e-4, n = 60).

This is the rule working, not a result being chosen: the decision is made
per run from host telemetry, is fixed in advance, is applied to every
condition identically, and both numbers are reported (the report's Execution
Integrity section names the runs excluded and why). It does show why the
rule must exist: two runs whose measurement window contained a host freeze
were enough to hide a near-linear relationship.

### Pipeline throughput (reproducibility)

The high-concurrency conditions write ~1e7 request rows per run; the dataset
totals ~9.2e7 requests / 12 GB, and `process.py` read `requests.csv` up to
three times per run with `csv.DictReader` (a dict per row) and sorted
multi-million-element Python lists for percentiles. Processing 955 runs did
not finish in 12 minutes and was killed. The file is now read once per run,
column-indexed, into flat arrays with `numpy` percentiles: the same 1010 runs
process in ~5 minutes. A report pipeline that cannot be re-run in reasonable
time is a reproducibility problem, not just an inconvenience.
